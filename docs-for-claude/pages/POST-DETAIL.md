# Post Detail Page

## Purpose

Standalone view of a single post, reached via the Home feed's "View post" button or a direct/shared link (`/posts/:id`). Audience: anonymous visitors (no auth required) — same public audience as Home.

## Data / API

- `GET /Posts/{id}` (public, per `AUTH.md`'s Endpoint Auth Reference) — fetched fresh on this route via `usePost(id)` (`features/posts/api/usePost.ts`), the same hook the admin Post Editor already uses. Always fetches independently rather than trusting Home's already-loaded list, since this route must work as a standalone shareable link (see `pages/HOME.md`).
- `PostReadModel` shape — see `pages/HOME.md` (same model, no separate type needed).

## Functionality & Interactions

- Route: `posts/:id`, public, sibling of the other top-level public routes in `app/router.tsx` (not under `/admin`).
- "Back to posts" link at the top, returns to `/`.
- Share button: copies this post's direct URL (`{origin}/posts/{id}`) to the clipboard and shows the shared success Toast ("Link copied") — same `notificationController.showSuccess` used by the global save-toast, and the same behavior as the Home feed card's share button (`features/posts/components/PostCard.tsx`).
- Loading: simple centered "Loading post..." text (this is a single-item fetch, not a list — no skeleton grid needed here unlike Home).
- Not found / error: centered "This post couldn't be found." message (covers both a real 404 and a fetch error — the API doesn't need to distinguish these client-side, both mean "can't show this post").

## Design / Visual Notes

- Single centered card, `max-w-2xl`, same glassmorphism/border treatment as `PostCard` (`THEME.md`'s Effects section): `border-2 border-accent` if pinned, otherwise `border border-border-default` (no hover-colorization here — hover-to-colorize is a list-affordance for "this is clickable," not meaningful on the page you're already on).
- Full `context` HTML rendered directly (`dangerouslySetInnerHTML`) — unlike the feed card's stripped-to-text preview, this is the full post, not a preview, so the original TipTap formatting (headings, lists) should render as authored. Since `context` is only ever authored by the Owner (single-user app, no third-party input), this doesn't carry the usual dangerouslySetInnerHTML/XSS risk of untrusted content.
  - **Real bug, fixed: manually-typed blank lines between paragraphs weren't visible on read, anywhere rich text is rendered — not just here.** Reported by the Owner as missing spacing; root cause was on the render side, not the backend and not TipTap's save behavior. Confirmed against `@tiptap/extension-paragraph`'s own `renderHTML` (`["p", attrs, 0]`, straight from source): a manually-typed blank line saves as a literal empty `<p></p>` node, no `<br>` filler — TipTap isn't dropping or trimming anything on save. The bug was that an empty, non-replaced block element with no content generates no line box at all under normal CSS, and Tailwind's Preflight zeroes every element's margin (`p { margin: 0 }`), so that empty `<p>` rendered at exactly zero height — the blank line was swallowed silently on the way to the screen, not before. **Fix:** `[&_p:empty]:min-h-lh` added to every `dangerouslySetInnerHTML` container in the app (this page, `pages/HOME.md`'s feed card, `pages/PROJECT-DETAIL.md`, and `CVTabs.tsx`'s Employment History) — gives an empty `<p>` a min-height of one line so it actually renders as the blank line it represents. Confirmed via a real round-trip in a real browser (not just reasoned from source): mocked HTML containing `<p>...</p><p></p><p>...</p>` rendered with a visible gap between paragraphs after the fix, none before.
- Gallery images (if any) rendered as a simple responsive image grid below the content — no lightbox/carousel for now, out of scope unless asked.
- **Thumb (if present) shown flush against the card's edges, with a flexible height that follows the image's own aspect ratio.** Reversed from a fixed `h-72 object-cover` banner (which cropped real image content) per Owner feedback — same change and same reasoning as the Home feed card's thumb (see `pages/HOME.md`): just `w-full`, no fixed height or `object-fit`, so Tailwind Preflight's default `height: auto` for `<img>` sizes it off its own intrinsic aspect ratio. Wider than the feed card's version in absolute terms only because this column (`max-w-2xl`) is wider, not because of any different sizing rule.
- "Back to posts" button: circular, sits on the card's left border (`-translate-x-1/2`, solid `bg-bg-surface`) **on desktop only now** — same technique as Project Detail's own back button (see `pages/project-detail.md` for the full positioning breakdown, since both pages share the exact same pattern/bug history).
  - **Mobile-only real bug, fixed: the button was clipped along its left edge.** The `-translate-x-1/2` bleed assumes a comfortable margin outside the `max-w-2xl` column — true on desktop, but on mobile the column fills `Container`'s full width, pushing the button ~2px past the viewport edge, hard-clipped by `body { overflow-x: hidden }` (`index.css`) into a visibly flat-edged circle. Fixed the same way as Project Detail: `left-1` (no bleed) below `md`, `md:left-0 md:-translate-x-1/2` (the original bleed) at `md` and up.
  - **Superseded by a second mobile-only fix, once the thumb's height stopped being a fixed constant.** The button used to sit at `top-64` — deliberately calculated to land vertically centered on the old fixed `h-72` thumb — falling back to `top-16` (aligned with the header row) only when there was no thumb at all. Once the thumb's height became flexible (see above), there was no longer a fixed number to center against, so both cases collapsed to the header-row position (`top-16`) unconditionally.
  - **Real bug, fixed: that unconditional `top-16` collided with the pin badge on mobile — something the old thumb-overlay position had accidentally never exposed.** On desktop this is harmless: the button's own left-border bleed (`-translate-x-1/2`) pushes it outside the card entirely, into real empty margin well clear of the pin badge sitting *inside* the card's own padding. On mobile there's no such bleed (see the clipping fix above) — the button sits inside roughly the same padding band as the header's pin badge (`absolute left-6`), and `getBoundingClientRect()` confirmed the two overlapped by ~18px horizontally and fully vertically whenever a post was pinned, regardless of title length. This had actually been latent in the no-thumb branch all along (nothing previously exercised "no thumb + pinned + top-16" together in a way that surfaced it) — unifying both branches to `top-16` just made it unconditional. **First fix:** mobile switched to `fixed top-24 left-4` instead of `absolute top-16 left-1` — pinned to the viewport rather than the card, positioned safely below the sticky site header (measured at 73px tall) rather than trying to dodge a title-length-dependent header height.
  - **Reversed per Owner feedback: mobile now centers the button on the viewport's vertical middle instead of sitting just below the header.** `top-24` was functional (no more overlap) but didn't read well positionally. `fixed top-1/2 -translate-y-1/2 left-4` — same centering technique `pages/PROJECTS.md`'s pager arrows already use (`top-1/2 -translate-y-1/2` against a `fixed` element centers on the viewport, not whatever ancestor it'd otherwise resolve against). `md:translate-y-0` cancels the translate back out at desktop, where `top-16` (no centering, an intentional fixed position matching Project Detail's own button) is unaffected. Confirmed via `getBoundingClientRect()`: mobile center lands at exactly half the viewport height and stays there through scrolling (still `position: fixed`); desktop unchanged at `position: absolute`, same `top: 137px` as before this whole chain of fixes started.

## Edge Cases

- No thumb: content starts directly at the title/meta row, no broken-image placeholder.
- No gallery: gallery grid section simply isn't rendered.
- Invalid/nonexistent `id`: falls into the same not-found message as a fetch error (see above) — no distinct "invalid ID format" client-side check, the backend 404 covers it.
