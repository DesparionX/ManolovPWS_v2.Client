# Projects Page

## Purpose

Public page showcasing all projects, grouped by their current state. Audience: anonymous visitors (no auth required).

## Data / API

- `GET /Projects` (public) — fetched once on page load, returns full `ProjectReadModel[]` array
- Client-side split into 4 groups based on the `state` field, rendered in this fixed order:
  1. `Finished`
  2. `InDevelopment`
  3. `Frozen`
  4. `Abandoned`
- `GET /Projects/{id}` (public) — called fresh when "View Project" is clicked, opening the full project detail route (same reasoning as Posts: must work as a standalone shareable link). Full detail page spec: `pages/PROJECT-DETAIL.md`.

`ProjectReadModel` shape (confirmed via `openapi.json` + `ProjectStateType` enum):

```ts
type ProjectState = "InDevelopment" | "Finished" | "Frozen" | "Abandoned";

interface ProjectReadModel {
  id: string;
  ownerId: string;
  name: string;
  description: string;
  state: ProjectState;
  liveUrl: string | null;
  gitHubUrl: string | null;
  uploadedDate: string; // date-only
  updatedDate: string | null;
  gallery: string[];
  thumb: string; // NOT nullable, unlike Posts.thumb — every project has a thumb
  stack: string[]; // tech stack tags, e.g. ["React", "PostgreSQL"]
}
```

## Functionality & Interactions

- Visitors browse grouped project cards; clicking "View Project" opens the full project detail (own route, fresh `GET /Projects/{id}` fetch)
- **Only one state group is shown at a time, paged via two circular arrow buttons** (`ProjectsPage.tsx`) — superseded an earlier version that stacked every non-empty group vertically as separate panels. Local `useState<number>` index into the filtered `groups` array; `goPrev`/`goNext` wrap around (last → first and back) rather than disabling the arrow at either end, since there's no natural "start"/"end" to a category list the way there is for, say, pagination through dated content.
- Full project detail page includes: name, full `description` (untruncated), `gallery` (all images, not just thumb), `stack` tags, `uploadedDate`/`updatedDate`, and two external links:
  - GitHub link — only rendered if `gitHubUrl` is not null
  - Live preview link — only rendered if `liveUrl` is not null
  - If neither is present, show neither button (no placeholder/disabled state needed)

## Design / Visual Notes

- Cards: same glassmorphism treatment as Home's `PostCard` — thin, low-opacity neutral border (`border-border-default/50`, no hover-colorization), `rounded-xl`, `bg-bg-surface/60` + `backdrop-blur-md`
- **No description preview on the card at all** — reversed after initially rendering the real HTML here (same as `PostCard`'s preview): per Owner feedback, the Projects page cards show *no* part of the description, full stop. Only thumb, name, and "View Project" remain.
- **Card heights are equalized within a row.** With the description gone, a project name alone can still wrap to a different number of lines per card, so cards could still end up visibly uneven heights without this. `ProjectCard.tsx`'s root `<article>` is `flex h-full flex-col` (CSS Grid's own default `align-items: stretch` already stretches each grid cell to the row's tallest — `h-full` is what makes the card's own box actually *fill* that stretched cell instead of just sizing to its content), with "View Project" pinned to the bottom via `mt-auto` rather than sitting wherever the (now short, variable) content happens to end.
- **Category panels page one at a time, sliding between each other** — a real slide (`transition-transform` + `translateX(-{index * 100}%)` on a `flex` track of `w-full shrink-0` slides, `overflow-hidden` on the parent), not an instant show/hide. **The panel has no horizontal margin of its own** — it spans the full slide width edge-to-edge, so it reads as one complete frame traveling the whole available width when paged, rather than a slightly-inset box with visible gaps at each side (an earlier version gave the panel `mx-2`, which is what caused both a visible gap and issue below). Two circular arrow buttons flank the panel — same style as `ProjectDetailPage`'s own back button (`rounded-full border border-border-default bg-bg-surface`, neutral `text-text-secondary` by default, not accent-colored — explicitly requested to match that button rather than `CVPage`'s own accent-colored pager arrows), positioned half-outside the panel's left/right edges. **Only rendered when there's more than one category** — with a single non-empty state, there's nothing to page between. **Arrows are siblings of the `overflow-hidden` track, not descendants of it** — the same real bug already hit once on `CVPage`'s own mobile pager (see `pages/CV.md`): inside the track, their half-outside-the-edge positioning would get clipped by the same `overflow-hidden` that exists to hide the other, off-screen category slides.
  - **Real bug, fixed: the arrows weren't horizontally centered on the panel's actual border.** The arrows are positioned against the outer `relative` wrapper, but the panel's `mx-2` margin (see above) inset its *visible* edges a few px from that same wrapper's edges — so the arrows landed a few px outside where the panel's border actually was, not straddling it. Removing the panel's `mx-2` (and fixing the glow-clipping concern that margin existed for, a different way — see below) makes the panel's true edges coincide exactly with where the arrows are positioned. **Confirmed via Playwright** (`getBoundingClientRect()` on both), not just eyeballed: arrow center and panel edge land on the exact same pixel. **Note: the arrows' own offset changed twice more since** — `left-0`/`right-0` when the `overflow-hidden` track had no horizontal padding, then `left-4`/`right-4` when the track briefly gained a shared `p-4`, and it's `left-4`/`right-4` *still* now that the horizontal clearance moved from the shared track onto each individual slide (see the peek-through bug below) — same 16px value, different element carrying it. The *principle* here (arrows must match wherever the panel's true edge actually is) is what's stayed constant across all of this, not any specific offset number.
  - **Real bug, fixed: the category label was clipped along its top edge — twice, actually.** The label sits on the panel's own top border via the "legend on border" convention (`absolute -top-3`, bleeding above the panel's own box), but the panel lives inside the pager's `overflow-hidden` track, whose own top edge coincided exactly with the panel's, leaving zero room for that bleed before the clip boundary. **First fix attempt was wrong**: added `pt-4` to the *outer* `relative` wrapper (parent of both the arrows and the `overflow-hidden` track), reasoning that it'd push everything down and create room. It didn't — padding on an ancestor *outside* an `overflow-hidden` box doesn't create any clearance *inside* that box; the box's own clip boundary stays flush with its first child's top regardless of how far down the page the whole unit sits, since the ancestor's padding just moves the whole composed unit as one piece. Confirmed wrong via `getBoundingClientRect()`: the label was still 11px above the clip line after that "fix." **Actual fix**: `pt-4` moved onto the `overflow-hidden` div itself — `overflow: hidden` clips at the *padding* edge, not the content edge, so padding on that specific element (not an ancestor of it) is genuinely inside the clipped area and gives the label's bleed real room. Same underlying idea as the CV hexagons' glow / CVPage's pager arrows fixes ("give the clipping ancestor a small buffer"), just landed on the wrong element the first time.
- **Per-category animated border glow, around the panel's frame, not each card.** Originally each *card* was wrapped in `.state-glow` (a conic-gradient/mask comet, shared with Home's pinned-post glow) — removed from `ProjectCard.tsx` entirely and replaced with a *different* technique applied to the category *panel* instead: `.category-trace` (`index.css`), ported from the CV page's hexagon badges (`.hex-trace`) rather than reusing `.state-glow` — a crisp SVG stroke-dasharray highlight animated along the panel's own rounded-rect border, plus a soft `drop-shadow` blur, rather than `.state-glow`'s more diffuse blurred comet. Still colored per-state via the same `--glow-color` custom property `PROJECT_STATE_GLOW_COLORS` already provided (`features/projects/types/projectTypes.ts`) — only the *effect* changed, not the color-per-state mapping (`THEME.md`'s Project State Colors section: `Finished` → `success` green, `InDevelopment` → `accent` cyan, `Frozen` → `frozen` indigo, `Abandoned` → `danger` red). `.state-glow` itself still exists in `index.css` and is still used by Home's pinned-post cards — this change only touches how Projects renders its own state color, not the shared class.
  - **Implemented as an SVG `<rect>` with `pathLength={100}`, not a fixed-size shape like the hexagons.** The hexagon badges could hardcode their exact stroke-dasharray/dashoffset numbers because badges are a fixed `h-12 w-14` — a category panel's size is responsive and varies by content (how many project cards, how many grid rows), so its perimeter isn't a fixed number. `pathLength={100}` on the `<rect>` normalizes the browser's stroke-dasharray/dashoffset math to a 0–100 scale regardless of the shape's actual rendered size, so `.category-trace`'s dasharray/keyframe work correctly no matter how wide or tall the panel ends up being. Confirmed both the `pathLength` normalization and SVG `calc()` in geometry attributes (used below) actually work in this app's target browsers via a throwaway Playwright test, rather than assumed from spec-reading alone.
  - **Real bug, fixed: the glow rendered as a tiny broken-looking fragment in the corner instead of tracing the whole panel.** Root cause: the `<svg>` had no explicit size — only `inset-1.5` (positioning offsets). That's enough to size a plain `<div>`, but `<svg>` is a *replaced element*, and replaced elements don't stretch to fill from inset offsets alone the way ordinary boxes do — with no explicit width/height (and no `viewBox`), it fell back to the browser's default replaced-element size, **300×150px**, floating in the panel's corner completely independent of the panel's real (large, responsive) size. Caught via `getBoundingClientRect()` on the actual `<svg>` in a real browser — invisible from reading the code, since nothing about `inset-1.5` *looks* wrong. Fixed by restoring an explicit `h-full w-full` alongside `inset-0` (matching the pattern the CV hexagons' own SVG already used correctly) so the `<svg>` genuinely fills the panel.
  - **The panel's visible border rect traces the panel's TRUE edge** (`x="0" y="0" width="100%" height="100%"`, `rx="12"` matching the section's own `rounded-xl`) **— not inset from it.** Went through an inset version first (`calc(100% - 20px)`, 10px in from the edge, both the border AND the glow) to keep the stroke width + drop-shadow blur clear of the `overflow-hidden` track's clip boundary (the panel has no margin of its own to bleed into) — but that visually read as **a second, disconnected "frame" floating inside the real one**, since it no longer lined up with the arrows or the section's own visible corners. Real bug, confirmed by the Owner: "Появила се е някаква друга рамка, а не трябва" (some other frame has appeared, and it shouldn't have). **Confirmed via `getBoundingClientRect()`**: the border rect's box, the section's own box, and both arrows' centers all resolve to the exact same coordinates.
  - **Real bug, fixed: a sliver of the adjacent (off-screen) category was visible at the panel's edge.** Clipping clearance for the glow's outward bleed (see below) was briefly given via a shared `p-4` on the `overflow-hidden` track itself (wrapping the *entire* multi-slide row, not just the current slide) — but `overflow: hidden` clips at that element's own padding edge, and padding sits *outside* each individual slide's box while still *inside* the overall clip boundary. That gap became a peephole: whatever rendered right at the start of the *next* slide (positioned immediately after the current one) showed through in that strip. Confirmed by the Owner via an annotated screenshot (red box around the visible fragment). Fixed by moving the horizontal clearance onto each individual slide instead (`px-4` per slide, not the shared track) — the track itself keeps only `py-4` (vertical, for the label's bleed; safe there since slides sit side-by-side horizontally, not stacked, so there's no adjacent slide above/below to peek into the same way). Clipping now happens exactly at each slide's own boundary, with no shared gap for a neighbor to leak through. The arrows' `left-4`/`right-4` didn't need to change again — same 16px value, now sourced from the slide instead of the track.
  - **Reversed per Owner feedback: the glow no longer hides behind the border — it traces its own path a few px *outside* it, and is thinner.** The previous pass mirrored the Contact page's Mail icon technique exactly (glow behind, a narrower solid stroke painted on top to mostly hide it, same path for both) — the Owner's actual intent was the opposite: the glow should only ever be visible from *outside* the frame, never hidden behind/under it. `.category-trace`'s glow `<rect>` now uses `x="-3" y="-3" width="calc(100% + 6px)" height="calc(100% + 6px)"` (a separate, slightly larger path than the border rect, not the same one) and `strokeWidth="2"` (down from `4`) — "по-тънък" (thinner), per feedback. The border rect stays solid `stroke-border-default`, `strokeWidth="2"`, at the true edge, unaffected — the two no longer share a path at all, so there's nothing for either to "hide" the other's line behind.
- **Methodology note:** this page's category pager went through four rounds of fixes the Owner reported back as wrong or broken before landing here. The bugs (SVG default-size fallback, padding landing on the wrong ancestor, an inset glow reading as a second frame, shared-wrapper padding leaking the adjacent slide) were all the kind that looked correct from the source alone and only showed up once actually rendered — visual/layout changes in this app get a real headless-browser screenshot + `getBoundingClientRect()` check before being called done, not just `tsc`/`build` passing.
- **Each state group gets its own glassed panel**, not just a bare heading + grid: `rounded-xl bg-bg-surface/40 backdrop-blur-md` wrapping that state's cards (its visible border is the SVG cover `<rect>` described above, not a CSS `border` class), with the section label sitting directly on the panel's top border (`absolute -top-3 left-6 px-3`, same "legend cuts into the border line" technique already used for the admin nav's collapse toggle and the Post/Project Detail back-buttons) — reads as a distinct grouped region per state, not just a plain label above a shared background.
- **Section heading label: `text-base font-semibold`** (bumped up from `text-sm` per Owner feedback — "a little bigger"), fixed render order (Finished, In Development, Frozen, Abandoned) via `STATE_ORDER` in `pages/ProjectsPage.tsx`, labels from the existing `PROJECT_STATE_LABELS` map (`features/projects/types/projectTypes.ts`). **Thicker/darker `text-shadow`** (stacked, near-black, blur radii up to 12px, opacities at or near 1 throughout) — per Owner feedback, same "faux-stroke via stacked shadows" convention `MessageDetailPage`'s field legends already use, needed for the same reason: the label sits directly on the panel's own border/glow and needs to stay legible against whatever's animating underneath it.
- **Not building here:** infinite/client-side scroll reveal like Home's feed — not called for in this doc, and portfolios are expected to have far fewer entries than a blog feed, so all groups just render in full

## Edge Cases

- **A state group with zero projects:** don't render an empty section heading with nothing under it — hide groups that have no projects rather than showing an empty "Frozen" heading with no cards (and, now that paging exists, such a group is never something the arrows can land on in the first place, since `groups` is already filtered to non-empty states before the pager is built)
- **A stale pager index** (e.g. the last project in the currently-viewed category gets deleted, shrinking `groups`): the displayed index is clamped (`Math.min(index, groups.length - 1)`) rather than trusted as-is, so it can't ever point past the end of a now-shorter array
- **No projects at all:** resolved — reuses the exact same placeholder pattern as Home's "Oooops!" (same `Frown` icon, same title), with project-specific body copy ("We have no projects yet or DB is dead.") instead of copy-pasting Home's post-specific wording. Confirmed: visual/tonal consistency with Home was preferred over a bespoke project-specific design.
