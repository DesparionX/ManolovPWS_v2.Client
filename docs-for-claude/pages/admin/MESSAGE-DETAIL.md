# Admin: Message Detail

Route: `/admin/inbox/:id`, nested under `AdminLayout` (per `admin-layout.md`) same as every other admin route — Owner-only, admin nav/shell visible around it. Reached only via the **Read** action on `INBOX.md`'s list.

## Purpose

Read-only view of a single contact message's full content. No editing, no replies — the only *automatic* interaction this page performs is marking the message as read; the only manual interaction is deleting it.

## Data / API

- **No dedicated `GET /Inbox/messages/{id}` endpoint exists** (confirmed via `openapi.json` — only `GET /Inbox/messages` as a list, plus `PUT`/`DELETE` by id). `PUT /Inbox/messages/{id}` doubles as this page's actual fetch: it returns the full updated `MessageReadModel`, so its response — not a lookup into the list's cached array — is what this page renders. Deliberately **not** derived from `useMessages()`'s cached list data, even though that would technically already have the fields: the point of this page is to hit the API by id directly, per explicit Owner correction (an earlier version read from the list cache instead, which worked but didn't actually call anything with the id when opening a message).
- `PUT /Inbox/messages/{id}` — no request body; marks the message as read server-side (if not already) and returns the current `MessageReadModel` either way. No button for this, and no branching on `isUnread` beforehand — see Functionality below for how/why it fires.
- `DELETE /Inbox/messages/{id}` — requires confirmation; on success, navigates back to `/admin/inbox`.

## Functionality & Interactions

- **Reading a message *is* what marks it as read — modeled as a query (`features/inbox/api/useReadMessage.ts`), not a mutation fired manually from an effect.** From the client's perspective the point of calling `PUT /Inbox/messages/{id}` here is "fetch this message's data" — that it also flips a server-side flag is a backend implementation detail, not something the client needs special mutation wiring for. `useReadMessage(id)` is a plain `useQuery` (same shape as `usePost.ts`), keyed by `queryKeys.inbox.detail(id)`, `enabled: Boolean(id)` — it fetches automatically on mount, with the standard `isLoading`/`isError`/`data` lifecycle, no manual `useEffect`/ref-guard needed.
  - **Revised from an earlier version** that fired this via `useMutation` + a `useEffect` + a ref keyed on `id` to fake "fetch on mount" — the mutation route reintroduced exactly the kind of manual-state-tracking bugs `useQuery` exists to avoid (see the git history around this file for the debugging trail). Modeling it as what it conceptually is — reading a resource by id — removes that whole class of problem.
  - **Keeping the Inbox list/badges in sync now happens globally, not per-hook.** TanStack Query v5 removed per-query `onSuccess`, so `shared/api/queryClient.ts`'s `QueryCache` config has a global `onSuccess` that checks `query.queryKey[0] === "inbox" && query.queryKey[1] === "message"` and invalidates `queryKeys.inbox.all` — which is what keeps `INBOX.md`'s list and both unread badges (`AdminLayout` nav, `Header`) reflecting the now-read state, without this page needing to know about them at all.
- **Nothing on this page is editable.** No form, no save button — just the message's own fields laid out for reading.
- **No "Back to Inbox" button** — removed per Owner feedback. Getting back to the list is just the browser/router back action; there's no in-page affordance for it beyond that.
- **Delete Message button, at the bottom of the page** — opens `ConfirmDialog`; on confirm, calls `DELETE /Inbox/messages/{id}` and navigates back to `/admin/inbox`. (`INBOX.md`'s list row also has its own delete action — both exist; deleting isn't exclusive to one location.)

## Design / Visual Notes

- Single column, `max-w-xl`, centered — this page has no complex layout needs (no image uploads, no rich text, no multi-field form), unlike the Post/Project editors
- **Each field is its own bordered box** (`DetailField` in `MessageDetailPage.tsx`) — one `rounded-xl border border-border-default` group per field, not one big box containing all of them. Same static field-group container style used for Profile's "Name"/"Address" boxes (`THEME.md`'s Field-group legends section): legend **left-offset** (`left-[10%]`, the usual convention — an earlier version centered it, reverted per Owner feedback), colored a shade darker than plain accent (`color-mix(in srgb, var(--color-accent) 80%, black)` — "one idea darker blue" per feedback, not the separate `--color-accent-dark` token, same reasoning as `FloatingInput`'s focused-label color in `THEME.md`). The value itself stays centered (`text-center`) under the legend.
  - **Revised from an earlier one-big-box version**: all six fields inside a single box with one "Message" legend, each as a `<dt>`/`<dd>` pair. Replaced per Owner feedback with the one-box-per-field layout described above.
- **Field boxes are sized per field, not all `w-full`.** `Title` caps at `max-w-sm`; `Name`/`Email` are narrower still, `max-w-xs`; `Message` (can be long, multi-line) caps at the wider `max-w-lg`. All share the same base padding, **symmetric top/bottom (`pt-5 pb-5`)** — an initial version used `pt-6 pb-3` (less bottom padding, matching the smaller clearance `FloatingInput`-style fields need since their legend only needs to clear the *first row* of content below it) but that made the vertically-centered value inside actually sit off-center within the box as a whole, since the surrounding padding itself was asymmetric even though the value's own flex-centering was correct; matching top/bottom padding was the actual fix, not additional centering logic. Extra height/alignment per field is handled via `DetailField`'s `valueClassName` prop (applied to the value's own wrapper) rather than more box padding — kept as a separate prop specifically so it doesn't fight the box's own padding for the same CSS properties (two conflicting padding utilities landing in the same class list is a real footgun elsewhere in this codebase — see `THEME.md`'s DatePicker label-color note for a case where exactly that silently picked the wrong one).
- **`Title`/`Name`/`Email` values are vertically centered within their box** (`valueClassName="flex min-h-5 items-center justify-center"`) — without an explicit min-height + flex-centering, a single short line just sits at its natural top-of-flow position under the legend rather than looking centered in the box's total height. The min-height (and the box padding above) were both trimmed down once already, per Owner feedback that the boxes read as taller than these short single-line values needed.
- **`Message`'s value is horizontally centered but top-aligned vertically** (`valueClassName="flex min-h-24 items-start justify-center"`, `items-start` not `items-center`) — deliberately different from `Title`/`Name`/`Email` above: a long, potentially multi-paragraph message reads better starting from the top of its (taller) box rather than vertically centered, which would look odd for anything short enough to leave a lot of empty space above and below.
- **`Name` and `Email` are deliberately different font weights** (`font-semibold` / `font-normal`, appended into the same `valueClassName`) despite sitting in visually-identical boxes — the name reads as the more prominent identity, the email as secondary/supporting.
- **Field order, top to bottom: IP/Device (side by side), Title, Name, Email, Message.** (`Name`/`Email` here are `senderName`/`senderEmail` — shortened from "Sender Name"/"Sender Email" now that each has its own box instead of sharing one with a "Sender" prefix doing that disambiguating work.) `sentDate` is deliberately not shown — the Owner-specified field list doesn't include it.
- **`senderMetadata`'s `ipAddress`/`userAgent` are not shown as boxes at all** — per Owner feedback they're rarely needed, so they're small **circular** icon buttons (`IconMeta` in `MessageDetailPage.tsx`: `rounded-full`, `Globe` for IP, `Monitor` for Device), placed above `Title` as the first thing on the page, that reveal the actual value in a hover tooltip instead of always taking up page space. The tooltip is a plain absolutely-positioned span (`opacity-0` → `group-hover:opacity-100`, matching the hover-reveal technique already used for Posts/Projects row actions), not a native `title` attribute — styled to match the app (`bg-bg-surface/95 backdrop-blur-md`) rather than the browser's default tooltip box.
- **Full `context` rendered with `whitespace-pre-wrap`, plain text — never `dangerouslySetInnerHTML`.** `context` is genuine user-submitted plain text from an anonymous, potentially adversarial visitor (per `CONTACT.md`'s validation notes), not TipTap-authored HTML like Post/Project content — same rendering approach `CONTACT.md` itself specifies.
- **Delete Message button sits below all the field boxes**, not inside any of them — it's an action, not a piece of the message's own data.

## Edge Cases

- Navigating directly to `/admin/inbox/:id` with an id that doesn't exist (typo'd URL, or the message was deleted in another tab/session) — `PUT /Inbox/messages/{id}` fails, shows "Message not found," doesn't crash or silently redirect
- Hard refresh landing directly on the detail route — no dependency on the list query having loaded first, since this page fetches independently by id; shows "Loading message..." until its own `PUT` call resolves
- Deleting the currently-open message from the list in another tab, then reloading/reopening this page — the `PUT` call fails the same as any other nonexistent id, falling into the "not found" state described above
